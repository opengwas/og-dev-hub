An indel’s ALID spells its reference allele first

Issue #381, under epic #367, built in epic #307’s run because #316’s integer key join keys on the ALID it defines. The owner decided the rule and where the reference comes from on 4 Nov 2026, and the two points left open then, and the format version, on 7 Nov. Format 0.2.2 (first numbered 0.2.1; see the note below). Amends ADR 0072 (its reversed-indel rule and its identity rules) and ADR 0036 §2 (its statement of the ALID convention). Points 6 and 7 record the owner’s rulings of 7 Nov on panel and GWAS-SSF indels.

Amended 11 Nov 2026 (the orchestrator’s ruling, epic #307’s merge of #432): this decision’s format is 0.2.2. It took 0.2.1 on #307’s integration branch, but main’s #430 released 0.2.1 first, in package 0.9.0, as “a Ragged release carrying regions.tsv”, and a released format cannot change its meaning. So reference-first indels take 0.2.2, the next unused version, on #430’s scheme of stamping each release the lowest version its features use (spec §21.3). Every build of this package spells indels reference first, so it writes 0.2.2, with or without regions.tsv. The converter stamps 0.2.0, keeping a 0.1.0 source’s sorted indels. A 0.2.1 Store, like a 0.2.0 one, sorts its indels: it is read and validated as package 0.9.0 reads it, and completion refuses it (see 5). Every rule below that this decision gated at 0.2.1 is gated at 0.2.2, and the text below now says 0.2.2 wherever it means this decision’s format.

Context

An ALID, chr:pos:A1:A2, sorted its two alleles. For an SNV that is right: the genome holds one base there, so A>G and G>A are one variant seen from either allele. For an indel it is wrong. A deletion written sorted is spelt exactly like the insertion of the same sequence, and at a tandem repeat both are real. FinnGen R13 BMI_IRN at 1:827587:

ref → alt rsid alt frequency beta se
G → GGGGCC – 0.0083 −0.0012 0.0136
GGGGCC → G rs755160762 0.0005 +0.0226 0.0506

Both were 1:827587:G:GGGGCC, and the deletion read as the insertion flipped. The same file holds 872,658 insertions and 1,071,490 deletions. 96,412 of the deletions share an ALID with an insertion in the same Analysis. The other 975,078 are stored under an ALID spelt like an insertion, and another Analysis reporting the insertion at that site joins them as one variant. None of this raised an error.

#357’s interim rule (ADR 0072, D5) kept the insertion of such a pair, where the source declares its reference, and dropped the deletion as duplicate_reversed_indel. Lone deletions kept the insertion’s spelling.

A reference genome does not settle it. Where the genome reads GGGGCC, both readings fit it. Left alignment normalises a ref/alt pair the source already gave; it cannot say which allele is the reference. Only the source’s own declaration tells the two variants apart.

Decision

1. The ALID. Where the two alleles are one length — an SNV, or a substitution of several bases — A1 is the alphabetically first and A2 the other, as before. Where their lengths differ, A1 is the reference allele and A2 the alternate (spec §4). BMI_IRN’s pair is 1:827587:G:GGGGCC and 1:827587:GGGGCC:G. An anchored indel’s shorter allele sorts first, so an insertion’s ALID is unchanged and a deletion’s is reversed. A statistic is signed for A1, as every statistic is, so a deletion’s z is now signed for its reference allele: FinnGen’s deletion, whose beta is for G, is stored negated.

The rule is opengwasdb.variants.normalise.alid_alleles. Every place an ALID is formed goes through it: canonical_alid, orient_to_canonical, and two hot-path forms that a contract test each holds to its answer, oriented_alid (a row) and alid_allele_arrays (a tabular reader’s projection, a block of rows at once). That covers each Source Reader’s rows and projections, routing’s sites and keys, the lift (statistics_swap), Variant Reference extraction and reading, the Hybrid fold’s key table, the Indexed Variant Subset list reader, the phenotype-SD pipeline and source fidelity. An LD panel’s ids are keyed and placed by canonical_panel_alid and indel_key (see 6), which the panel table’s builder imports. The one other spelling is a Store’s from before 0.2.2, sorted_alid_alleles, which only reads such a Store (see 5).

variant_table.indel_order (see 5) forms no ALID. It judges a Store’s own ALIDs against the table’s other columns, by the table alone, and does not call these functions: on purpose, so a defect in them cannot pass its own check.

2. Where the reference comes from. Only from the source’s declaration (orient_to_canonical(..., other_is_reference=), required wherever an ALID is formed from a row):

  • declared: GWAS-VCF’s REF, FinnGen r13’s ref, and a ref_alt_effect_is_alt Column Map’s ref;
  • declared row by row: a GWAS-SSF file whose harmonised alleles are its main columns, on a row whose harmoniser code is 10 or 11 (see 7);
  • not declared: every other GWAS-SSF row (see 7); a BESD .esi’s A1 and A2; a build-dense association TSV; an effect_and_other Column Map; and a ref_alt_and_effect_allele (dbGaP MVP) Column Map, whose ref nothing in this package documents as the genome’s.

An indel whose source declares no reference names no ALID. It is a malformed identity, like a missing chromosome (#365): the reader leaves it out of both of its streams and names it in the stream’s tally (UndeclaredReference), and Association Admission counts and logs it per Analysis as indel_reference_undeclared, after allele_invalid in precedence (ADR 0072), or, for GWAS-SSF, under a reason naming its layout (see 7). It is never stored under a guessed order. Its SNVs and substitutions are stored as before. The rule set’s version moves to admission/13.

3. After a lift, “reference” is the release assembly’s (GRCh38): the source’s declared reference projected onto it, complemented on a reverse-strand chain block. A lift therefore never re-orients an indel.

4. Equal-length multi-base substitutions stay sorted, like SNVs: the genome holds one sequence there, so their two orders are one variant.

5. format_version steps to 0.2.2, the compatible remainder (spec §21.1). The arrays are 0.2.0’s; only an indel’s ALID and the sign of its statistic change.

  • A 0.2.0 Store is read as before. Its indel ALIDs keep their sorted spelling, and nothing rewrites them. A source-fidelity check spells a source’s indels sorted against such a Store (sorted_alid_alleles), and signs them with it (validate --source).
  • The converter writes 0.2.0, not the current version: a 0.1.0 Store sorts its indels and says nowhere which allele is the reference, so its copy cannot honestly be stamped 0.2.2 (format_version_for with reference_first_indels=False).
  • Completion refuses a 0.2.1, 0.2.0 or 0.1.0 source. It writes into its source’s arrays and keeps its format (ADR 0038 §4), and completing such a source would add panel ALIDs spelt by this rule beside the source’s own deletions spelt like insertions. The source is rebuilt, then completed.
  • A new Validation Rule, variant_table.indel_order, judges a Store from 0.2.2 on: each indel row’s ALID spells its alleles as the row records them, its effect_allele then other_allele, and a lifted variant’s source_alid spells the same allele first, a lift never changing an allele’s length. A 0.2.1, 0.2.0 or 0.1.0 Store is not judged by it. What it cannot see is a same-assembly Store whose builder spelt a deletion sorted throughout, table columns included: nothing in such a Store records the reference apart from the ALID itself.
  • #338’s reference branch also used 0.2.1. If it lands after this, it takes the next step, 0.2.3.

6. An LD Reference Panel places an indel by a declared reference, settled by GRCh38 evidence where the panel declares none (owner, 7 Nov). A panel names each variant by an id with its alleles sorted, and every panel on the IEU host does so for its indels: 648,392 in UKB EUR and 2.1–3.2 M in each HGDP+1kGP panel, none unsorted (13,124,104 in all). UKB’s own .afreq marks all 9,848,829 rows PROVISIONAL_REF?=Y. Against GRCh38 evidence (the HGDP+1kGP pvars, gnomAD v3.1.2’s REF/ALT), UKB’s id-first allele is the reference for 30.8% of 586,364 indels the evidence reads one way and its OA for 69.2%, so neither column declares it. So:

  • A panel with a REF column (the HGDP+1kGP AMR panel, whose REF matches the genome’s at all 1,989,545 sites read one way) places each indel by it.
  • A panel without one (UKB EUR, HGDP+1kGP AFR/EAS/EUR/SAS) places it by the indel-reference table beside its blocks, ld_dir/{ancestry}/ indel_reference.tsv.gz (tabix-indexed), with indel_reference.json beside it: the evidence files and their checksums, the script’s revision, and the counts by outcome. scripts/build_panel_indel_reference.py writes both and never replaces either, and fails, writing neither, on an evidence file it cannot read to its end. Completion reads a table only beside its provenance, and only while the table’s sha256 is the table_sha256 that provenance records; it refuses any other table. The script settles an indel by the HGDP+1kGP pvars and FinnGen R13’s declared ref, only where a source reads the key one way and no source reads it otherwise; a key a source holds both ways (the insertion and the deletion both exist), one the sources read differently, and one no source holds are left unsettled, each counted.
  • A panel with neither places no indel, and says so in completion’s log and its record.

The tables written on 7 Nov 2026 (script at ccb7156; evidence the 110 HGDP+1kGP pvars and FinnGen R13 BMI_IRN, checksummed in each indel_reference.json):

The HGDP+1kGP AMR panel needs no table: its REF column places all of its indels, 2,660,493 unique keys (2,660,509 summed over LD blocks, as a completion record counts them; see below). Of UKB’s settled indels, 409,287 are deletions; 367,799 of them are deletions OGS-00017 (FinnGen R13) observes, and a rebuild of it at 0.2.2 spells each as the panel does, where completing its 0.2.0 Store with the sorted rule would have put 364,124 of them under a second spelling.

canonical_panel_alid names an unsettled indel no ALID, so completion neither matches nor fills it: a fill there is dropped and counted nowhere, and an observed indel stays observed.

Clarified 11 Nov 2026 (the owner’s ruling): a panel indel this point names no ALID is counted neither imputed nor missing in completion_quality, inside a region or out, at a shared endpoint or not. It is no row of any Store, and a block’s counts describe only rows the Store holds (ADR 0039), so a quality row’s n_imputed + n_missing is the rows completion added that Analysis that the block owns. This point first said such a fill “counts as missing”; that rule is withdrawn. The completion record still counts every such indel, in provenance.completion.panel_indels (unplaced.no_reference, and n_indels less n_placed).

A panel codes its eigenvectors and EAF on each row’s EA (the sorted-first allele, construct_block.py), and a statistic is signed for the ALID’s A1, so a row whose A1 is not its EA – every settled panel deletion – has its eigenvector row negated and its frequency complemented when its block is read (LDBlock.flipped). The same rule holds an SNV whose EA were not its A1; on the host’s panels none is. A row with no EA (an empty cell, or a block with no EA column), or with an EA that is neither of its alleles, names no ALID, SNV or indel, since nothing says which allele its LD is for. Every block of the six panels has an EA column, and none of their 64,785,257 rows is such a row.

A completion records how its panel placed its rows. In provenance.completion.panel_indels: reference_from, each table read with its checksum, counts and revision, the indels read and placed, and unplaced, the indels not placed by reason, which sum to the difference: no_reference, no_effect_allele, effect_allele_not_an_allele, and identity_invalid (an id no ALID can spell, once its reference is found). In provenance.completion.panel_snvs_unplaced: the SNVs and substitutions not placed, by the last three reasons. Every count is summed over LD blocks: an indel on a block boundary counts once per block. So AFR’s record places 2,388,315 indels where its table settles 2,388,309 keys, and AMR’s counts 2,660,509 where its panel holds 2,660,493.

7. GWAS-SSF declares its reference by layout and harmoniser code (owner, 7 Nov; it supersedes the 4 Nov rule for code 11). The reader tells the layout from the header:

  • harmonised alleles in the main columns, hm_code beside them (4,595 of the host’s 6,078 harmonised files): a row whose code is 10 or 11 declares its other_allele the reference; any other code drops its indels (indel_ssf_hm_code);
  • the study’s alleles in the main columns, harmonised ones in hm_other_allele/hm_effect_allele (1,483 files): every indel is dropped (indel_ssf_hm_columns);
  • no harmoniser column (a filtered file, for example OGS-00006’s): every indel is dropped (indel_ssf_unharmonised), as decided on 4 Nov for a file not harmonised;
  • any other mix of harmoniser columns fits neither layout, and nothing says which columns hold its harmonised alleles, so the file is refused, never read under a default.

Each record counts, per Analysis, the indel rows the code rule kept (indel_rows_kept_by_hm_code: rows read, before duplicates are resolved) beside those each reason dropped, so a Release says how many indels it took on this rule.

File by file it is less even: code 11 is below 95% in 51 of 131 files and code 10 in 19 of 130 (for example GCST90837174’s code-11 deletions, 412 of 76,810), mostly the deletions of each file’s minority code. Rescued copies keep the raw file’s alleles (owner, 7 Nov). The 58 swap_alleles copies under derived/ebi-gwas-catalog/ (opengwasdb-stores #155) exchanged the allele columns but kept hm_code, so in them effect_allele was the reference and this rule would read the wrong allele on every indel row. A record of them exists, derived/ebi-gwas-catalog/eur-hybrid-rescue-orientation-manifest.tsv (each file’s checksum, and “rescued via swap_alleles”), but nothing in this package reads it, and no build manifest named a rescued copy. The rescue was redone in opengwasdb-stores instead: it keeps effect_allele and other_allele as the raw file has them, so other_allele stays the reference, and rewrites the statistics, negating beta, inverting an odds ratio and its interval, and complementing the frequency. A rescued copy is then read like any other file of its layout, and the engine needs no signal and no guard.

The 56 regenerated copies and the manifest were replaced under derived/ebi-gwas-catalog/, and all 56 live checksums were verified against the receipt. The regenerated copies had been checked against 577,093,421 raw rows with zero mismatches. GCST90275159 and GCST90275160 were excluded because their beta and SE are dummy effects; their manifest rows name no data files, and their old derived copies remain on disk unused. This data operation is complete; the code is still in draft opengwasdb-stores#457, which must land before anything rebuilds OGS-00011.

8. #357’s reversed-indel rule no longer fires. An insertion and a deletion at one position are two variants, and an indel whose source declares no reference never reaches a place, so no build drops a row as duplicate_reversed_indel. The reason stays readable in records written before. Routing still carries each row’s declaration (REFERENCE_*), now REFERENCE_FIRST for every declared indel. The rule’s branch, REFERENCE_SECOND and ReferenceAllele.ALT are unreachable, and stay only until #316 removes them.

Clarified 7 Nov 2026 (#316). They are removed, with the per-row REFERENCE_* codes and the readers’ ref_first, which only the rule read, and the reference arrays of a Hybrid’s Overflow and off-reference spills. Routing no longer carries a row’s declaration. duplicate_reversed_indel keeps its place among the reasons, retired, because a reason’s code is its position (ADR 0072’s clarification of 7 Nov).

9. Variant References declare their indel semantics (owner, 16 Nov 2026, issue #381). The installed plain references still contain historical sorted indels. A sorted deletion is indistinguishable from a valid reference-first insertion, so rejecting only sorted rows cannot preserve the valid case and reject the unsafe one.

The first physical line of a newly regenerated reference is #opengwasdb-variant-reference<TAB>1 plus a newline. Version 1 declares reference-first indels; it is separate from a Store’s format version. It works before either a plain ALID list or a table header, in text or gzip. Both artifact writers emit it, including the streaming extractor’s header gzip member. The shared reader retains the resolver’s case-insensitive alid, variant_id and id headers with generic whitespace splitting, including mixed tabs/spaces and independent header/row padding, and unheaded first-row ALIDs. Routed artifacts keep tab-precise empty fields; the declaration rule does not narrow those existing SNV input shapes. An unmarked input containing an indel is refused at its first indel, naming the row/ALID and requiring regeneration; unmarked SNVs and equal-length substitutions remain usable. Unknown versions and misplaced declarations are refused. No allele is automatically swapped, and a marker is never a license to relabel legacy bytes without regenerating their identities from declared references.

Marker parsing and refusal belong to the Variant Reference module. Its full reader and streaming iterator share them; Hybrid’s legacy panel loader, the resolver and BESD’s streamed lift reference use adapters to that iterator. They read to the end even when no positions are wanted. A detached Store Variant Table has no exemption, even beside a manifest: these interfaces do not open and verify its Store Release envelope. In-memory references and writer inputs remain the caller’s responsibility to form under this ADR.

The declaration’s tab makes the previous full reader refuse an unknown header rather than read a new artifact as a plain list without routing. Older independent readers do not all refuse it, so using a declared reference requires upgrading the engine. This changes the Variant Reference input contract, not a Store Release’s format or how existing Stores are queried. Regeneration of the large installed references remains separate work.

Considered

  • Sorted ALIDs with a flag recording the orientation. Keeps 0.2.0’s spellings, but every reader and joiner would have to read the flag to tell a deletion from an insertion, and one that did not would join them in silence: the defect this ADR removes.
  • Read the reference from a genome FASTA. None is on the host, and at a repeat both readings fit the genome.
  • Read the panel’s reference from its SNP id, or from OA. Each is wrong for 30.8% or 69.2% of UKB’s indels the evidence reads one way.
  • Keep an undeclared indel under its sorted spelling. That is the ambiguity itself, now in a format that claims to have removed it.
  • GWAS-SSF code 11 alone, as decided on 4 Nov. In the main-column layout code 10 is the more reliable code and 69% of indel rows; dropping it would lose them for no accuracy (7).
  • Dropping every GWAS-SSF indel, which no code-keyed error can reach. The owner chose to keep codes 10 and 11 and accept the residual error (7).
  • Reading a rescued copy’s reference from its path, or from the rescue record. Either makes the engine depend on opengwasdb-stores’ layout; a rescue that keeps the raw alleles needs neither (7).
  • Detect a historical reference from sorted indels or a filename. A valid insertion has the same spelling; a mixture of orders proves nothing about each row. A versioned producer declaration establishes the input convention without guessing (9).

Consequences

  • Until the published Releases are repaired or rebuilt (#367, #382), a published Store and a new Store spell a deletion differently, and a lone deletion’s z has the opposite sign in the two. A query by 1:827587:G:GGGGCC finds the insertion in a new Store and, in a published one, whichever row the build kept.
  • Rebuilt from its sources, the FinnGen R13 pilot OGS-00003 holds 96,428 more variants: each a deletion that now has its own row beside its insertion. Its other 975,140 deletions are respelt, their z negated and EAF complemented. Every other cell keeps its z and EAF, but 198,820,410 of them decode an SE up to one int8_residual step (0.39%) away: each Analysis’s se_coefficients are fitted over the cells it stores, and the new deletion rows move them by up to 1.9e-5.
  • Stores built from BESD or build-dense sources, or from GWAS-SSF files in the hm_* layout or with no harmoniser column, hold no indels; each is logged in its build’s Admission record. GWAS-SSF files in the main-column layout keep their code-10 and code-11 indels: all but 371 of the 96,420,588 indel rows of the 197 files checked.
  • A completion places a panel indel only by the panel’s REF column or its indel-reference table, and fills nothing at the rest.
  • The owner-approved 10 November 2026 operation replaced 56 regenerated swap_alleles copies and their manifest under derived/ebi-gwas-catalog/; their live checksums match the receipt. GCST90275159 and GCST90275160 are excluded because they use dummy effects, with their old copies unused (7). The data operation is complete; the code PR, opengwasdb-stores#457, remains draft and must land before anything rebuilds OGS-00011.
  • A package that knows only 0.2.0 or 0.2.1 reads a 0.2.2 Store’s data as written and warns that it is newer; a completion it ran would spell its panel’s indels sorted beside the Store’s reference-first deletions. Only a package that knows 0.2.2 completes one. Package 0.9.0’s validate also fails every 0.2.2 Store, on its stamp rule: “release is stamped 0.2.2, but a release carrying no region table is 0.2.0” (or “… regions.tsv is 0.2.1”). The fix is to upgrade the package, not to re-stamp the Store, which would let 0.9.0 complete it. This package does not judge the stamp of a Store newer than 0.2.2: it warns that the package must be upgraded. (Amended 12 Nov 2026, epic #307’s review: this point first said such a package reads a 0.2.2 Store “correctly” and left out its validate.)
  • An unmarked Variant Reference containing indels, including a detached Store Variant Table, now fails before routing. Regenerate it with the versioned reference-first declaration (9); existing SNV-only references remain usable.
  • Breaking for Python callers: orient_to_canonical, oriented_alid, identity_fault, project_source_variant and oriented_variant take a required other_is_reference, orient_or_drop a required declaration and row, and the tabular projection columns a required reference.

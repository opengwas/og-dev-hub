The site

How this site is built, previewed, published and extended. It is one Quarto website over this repository’s docs/ and opengwasdb’s docs, rendered on the host where the data lives, and published from the gh-pages branch at https://blog.opengwas.io/opengwasdb-stores/.

The commands

Command What it does
pixi run site Collect the site’s data, stage both repositories’ docs, render, and check every served path. The render runs over 24 Quarto processes; --jobs N changes that, and --jobs 1 is Quarto rendering alone.
pixi run site-preview The same staging, then Quarto’s live-reloading preview (on http://localhost:4200, or the next free port).
pixi run site-publish --dry-run Render a clean checkout of origin/main and commit it to gh-pages without pushing. It takes --jobs too.
pixi run site-publish The same, then push gh-pages. The owner runs this.
pixi run docs Refresh a report: render its .qmd and copy the HTML to the name the site serves.

Nothing is rendered in CI: every page repeats the site’s navigation, so committed output would make parallel pull requests conflict.

Where a render puts things

Path What
/data/opengwasdb/work/site/<checkout>/_site The rendered site ($OPENGWASDB_SITE_OUT overrides it).
/data/opengwasdb/work/site/<checkout>/_stage The mirror of docs/ the render reads, with the collected data and the generated pages in it ($OPENGWASDB_SITE_ROOT moves the work root).
/data/opengwasdb/work/site/<checkout>/_site-workers-* Each render worker’s copy of the mirror, and what it rendered, while a render runs. Removed when the render ends, whether it succeeded or not.
/data/opengwasdb/work/site/<checkout>/_preview The synced copy site-preview serves; Quarto renders inside it.
/data/opengwasdb/work/site/opengwasdb.git The bare clone the engine’s docs are staged from ($OPENGWASDB_SITE_ENGINE_CLONE overrides it).

Nothing the site build writes goes under /home or /tmp, and nothing is written into the checkout.

The render reads a mirror of docs/, not docs/ itself. That is deliberate: the mirror is where the link rewrite, the Mermaid spelling and the staged engine docs and glossary live, so no source file is ever edited, docs/ stays readable on GitHub, and two renders — of different checkouts, or of one checkout into two outputs — never collide. docs/opengwasdb/ holds the engine’s docs at the pinned revision and docs/glossary.md is CONTEXT.md, both inside the mirror.

How a render runs in parallel

Quarto renders a project’s pages one after another, about a second each whatever the page, so the 226 pages took five minutes. Quarto cannot render in parallel itself, so src/project_site/render.py does it from outside:

  1. One page is rendered alone in a copy of the mirror. Quarto runs the pre-render hook first, so the generated pages exist, and quarto inspect lists every page the site has.
  2. Each worker renders pages in its own copy of the mirror, one quarto render <page> call per page. A call renders one page but builds its navigation from the whole site, so a page is the same whichever worker renders it.
  3. The outputs are merged. A page comes from the worker that rendered it, every other file must be identical in every worker or the render stops, and the search index and sitemap are rebuilt page by page.

On 4 Nov 2026 the render of main took 319 s with Quarto alone and 67 s over 24 workers. Of the 471 files the two renders share besides the search index and sitemap, 470 were byte-identical. The other was architecture-structure.html, whose registry diagram Quarto’s Graphviz lays out differently from one render to the next, even of the same source. The search index held the same 1,155 entries and the sitemap the same 226 addresses.

site-preview is unchanged: Quarto’s preview renders the site itself before serving it.

Publishing

site-publish renders a clean detached worktree of the ref, so nothing depends on an uncommitted change in your checkout, and commits the output to a gh-pages worktree with a message naming the source commit. It creates gh-pages as an orphan branch when it is absent, so the published branch shares no history with a source branch.

It refuses a ref that is not on the remote, and it refuses a gh-pages worktree with uncommitted changes, because a publish replaces what that worktree holds.

The default ref is origin/main: every merge lands there and is a version (#386). Before the cutover, name --ref origin/dev explicitly.

The data pages

Five pages are generated from the site’s own data rather than written by hand: the Overview, Stores, Epics, Trends and Changelog, with one page per epic and one per registered Store beside them (src/project_site/pages.py, #391).

Three more, under Architecture in the navbar, draw how OpenGWASDB fits together from both repositories’ docs/architecture/components.yaml and their code (src/project_site/architecture_pages.py, #418): Pipeline (the stages, their components and ADRs) and Structure and health (context, containers and components, the engine by layer with its upward imports, and the gaps in the claims). The third, Work map (#419), shows where live work meets: which epics’, tickets’ and branches’ files fall on the same component, and whether a blocking edge between the specific tickets coordinates it. It shows pushed branches and the files tickets cite, says when it was measured, and says that branches existing only on a build host are not shown; pixi run architecture conflicts run on that host includes them. The engine is read at its main from the same bare clone the docs come from; the docs stay at the pinned tag. The diagrams are Quarto {dot} cells, drawn at render time, so no SVG is committed. Each page says what is written by hand and what is measured, and docs/spec/project-site.md (Architecture) is the contract.

  • pixi run site and site-publish collect the data themselves before the render, into the render’s own _stage/_data, from the stores/ and docs/_epics/ of the checkout being rendered. $OPENGWASDB_SITE_DATA names a directory collected already, and then nothing is collected.
  • docs/_quarto.yml names docs/pre-render.sh as the project’s pre-render hook. Quarto runs it inside the mirror before rendering, so the generator writes the pages where the render reads them and never into the checkout. The commit being rendered reaches it as $OPENGWASDB_SITE_COMMIT, which is what a generated link to a file outside docs/ names.
  • The five section pages are committed as short stubs that say they are generated: their published paths stay (index.html, stores.html), and a render replaces them. The per-epic and per-Store pages are git-ignored (docs/epics/, docs/stores/).
  • A page never fails because a source is missing: it shows a notice naming the source, its error and when it was collected. docs/spec/project-site.md is the contract between the data and the pages.
  • An epic page is written for every epic the board lists and for every valid epic record: a record outlives the board, so when gh is offline the record-backed page is still generated, carrying the board’s unavailable notice, and a page that has a record is never removed as stale.
  • The Overview reports progress for the board’s open Milestones only. A closed Milestone is a plan nobody is working to any more, so it appears as one short line under them — Closed: Milestone: First release (#91) — and never with a count of lines met or to go.
  • A yardstick trend is drawn within one workload. Results are keyed by workload_sha256 (workload_id where the hash is missing), each series and each matrix table names the workload it measured, and no line or row spans two workloads, so a trend shows a change in the code rather than in the benchmark. A point measured before 2026-11-02 in the Veeam backup window (veeam_window: true, which no run since records) is ringed in the figure and marked † in the table, with a caveat saying its timing is not comparable.
  • A Store page shows its own size and query performance from the newest yardstick result that measured it, naming that result, its workload and the opengwasdb version it ran on, and says so when the newest result lists the Store as pending or no result names it.

Going live

The first real publish creates gh-pages; GitHub Pages keeps serving the legacy main/docs deployment until its source is switched. That switch is the owner’s step, taken after the first real pixi run site-publish:

gh api -X PUT repos/opengwas/opengwasdb-stores/pages \
  -f 'source[branch]=gh-pages' -f 'source[path]=/'

It sets Pages to build from the gh-pages branch at /, which is where site-publish puts the rendered site.

Adding a page

  1. Add a Markdown file under docs/ — docs/my-page.md — with a single # heading as its title. It is served at /my-page.html.
  2. If it belongs to a section, add it to docs/_quarto.yml: the navbar for a section index, or a sidebar’s contents. A glob such as adr/*.md already covers a new ADR, so most pages need no configuration.
  3. Use ```mermaid for a diagram and it renders as one, as it does on GitHub; dot files under docs/diagrams/ are served as the files they are. Quarto renders a Mermaid cell only in a .qmd, so a .md page holding one is staged as .qmd, its published .md path is filled in after the render, and links to it reach its rendered page. Add it to the sidebar as <name>.qmd.
  4. Link to a sibling with its relative path (../spec/release-config.md). Link to anything outside docs/ with the relative path you would use on GitHub — the build rewrites it to that file on GitHub at the commit being rendered. A link the build rewrites is reported if the commit does not have the target.
  5. Never move or rename a page that is already published. A reader’s link would break. If a page must move, keep the old path as an aliases entry in the new page’s YAML front matter; Quarto then writes a redirect page there, which the served-path check counts as an alias rather than a missing path.
  6. Historical reports are not rendered: their source .qmd lives in docs/reports/, and pixi run docs renders it and copies the self-contained HTML to the root name the site serves. Do not add .qmd files to docs/ outside reports/ unless the page really must execute code at render time.
  7. A page that is computed from the site’s data is not written by hand: add it to src/project_site/pages.py (SECTION_PAGES for a section, or one of the per-epic and per-Store writers) and commit a stub with its published path at docs/, as the data pages above do. Do not edit a generated page — a render replaces it. A page holding a chart is written as a {=html} block, not an inline SVG in a table cell: Pandoc drops an SVG’s children there.
  8. A fact is data, never markup, and that includes a fact in a code span: a version tag is free text, so it may hold a backtick, a | or a <b>. Write one with pages._code, which uses a plain code span when the value cannot close it or cut its table cell and an HTML <code> with escaped text otherwise; a hand-written `{value}` fence breaks on the first one that does.

Checking a change

pixi run site ends with the served-path check: every path in resources/site/legacy-served-paths.txt must be present or aliased in the output, and a missing path fails the build. Run it before opening a pull request that touches docs/.

That baseline is fixed, and deliberately: it is the 90 paths under docs/ at ff204b6, the commit the live legacy Pages deployment was built from, so it protects the links readers already hold. A page the site generates (an epic, a Store, a trend) may come or go without touching it; only a legacy path that a reader can still follow is in it, and a path leaves it only when a legacy URL is retired deliberately, by a reviewed change to the file. A missing, empty or unreadable baseline file fails the check rather than passing an unchecked render (src/project_site/build.py).

You can run the check on its own against an existing render:

pixi run -e dev python3 -m project_site.urlcheck \
  --paths-file resources/site/legacy-served-paths.txt \
  --output /data/opengwasdb/work/site/<checkout>/_site

For an ad-hoc answer to “does this render serve everything main’s docs/ held at some revision?”, name the revision instead:

pixi run -e dev python3 -m project_site.urlcheck \
  --git-rev ff204b6 \
  --output /data/opengwasdb/work/site/<checkout>/_site
